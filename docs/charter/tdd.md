# TDD方針

各プロジェクトでは、テストを以下の`TDD方針`にまとめ、開発においてはこれを基本とする。

プロダクト仕様の正本は、各プロジェクトの `docs/main.md` および `docs/specs/`。  
アーキテクチャ: [thin-ddd.md](./thin-ddd.md)

## TDD

- ここでいう`TDD`とは、`テスト駆動開発`のことである。
- 各プロジェクトでは、テストを自動化し、TDDで開発を行う。

## TDDで行うテストの分類

- 単体テスト: ロジック単位のテスト。１つの関数または１つのメソッドに対して、必ず存在する。
- 結合テスト: 複数のロジックが組み合わさったテスト。上記と同じく、1つの関数または1つのメソッドに対して存在する。
- DBテスト: 実際にDBと接続してCRUDするテスト。
  - [薄いDDD](./thin-ddd.md)と組み合わせ、DB CRUDの抽象化層（**Repository層**）のみ、インメモリのDB（またはテスト用SQLite）でテストを行う。
  - ここでDBのCRUDを担保することにより、他のロジックは、テストではモックでのみテストが成立する。
  - DBを持たないプロジェクトでは不要。
- E2Eテスト: ヘッドレスブラウザを用いたテスト。初期・MVPでは必須としない。UI固まり後に最小検討する。
- ビジュアルリグレッションテスト: UIの差分を検証する。当面は必須としない。

## テストパターン

いわゆる`ピラミッドパターン`をベースに、発展させた**氷山パターン**を採用する。

ピラミッドパターンは

- 単体・結合は厚め
- E2Eは薄め

という形で、下層ほど広く、上層ほど小さく行うものである。

これは、E2Eテストに時間コストがかかりやすい、ということから考えだされたものである。

しかしながら、プロジェクトによっては、単純なロジックだけでも肥大になる場合があり、これを過度に守ると初期リリースに時間がかかりすぎる場合がある。

そこで、発展した**氷山パターン**は、以下のように考える。

- 単純なロジックは、静的エラーが出ていなければ、一定の品質を保っていると考える
- ピラミッドパターンに比して、単体・結合は薄めにして良い
- E2Eに対する考え方は同じ

つまり、静的エラーで担保する部分は、氷山でいう「水面以下」の部分であり、「水面以上」の部分に関してのみ、既存のピラミッドパターンを適用する。

これにより、ピラミッドの容積そのものを減らすことになり、肥大化する自動テストの軽減が可能となる。

一方で、単体・結合テストはソフトウェアの品質担保に重要な部分であり、単純にテストを減らすことは危険である。

そこで、氷山パターンでは

- 単体・結合テストそのものは、減らさない
- 一方で、初期リリースまでの間は、過剰なカバレッジを追わない

とする。

氷山パターンでは、カバレッジは概ね`50%`を目安とする。

### E2Eテストの方針

- UIを伴わない初期の開発、および MVP では不要。
- 開発後半、リリース前で採用を検討する。
- シナリオは、必要最低限のものに絞る。そのシステムの利用にあたって、クリティカルなもののみに限定する。
  - （一般例）ログイン・ログアウト / サインアップ / 決済 / よく使うコンテンツのCRUD

## TDD開発の実際

- 仕様書がFIXする（各プロジェクトの `docs/main.md` / `docs/specs/`）。
- 仕様書に基づき、`テスト仕様書`を書く。
- テスト仕様書の配置場所・分割は、各プロジェクトに依る。原則は `docs/tests/`。ドメイン別フォルダに分割してよい。
- テスト仕様書には、規定のフォーマットに従って記述する。
- テスト仕様書がFIXしたら、先にテストを書く。
- テスト仕様書の書き方は後述。
- テスト仕様書がFIXしたら、Red -> Green -> Refactorの順で実装。
- 最終的にテストが通ったことを確認して、機能実装を完了とする。

## テスト仕様書の書き方

- テスト仕様書の配置場所・分割は、各プロジェクトに依る。
- 見出しは、ロジック（関数またはメソッド）の名前とする。
- 直後に、自然言語で大まかな処理の内容を記述。
- 小見出しで、テストを正常系と異常系に分けて記載する。
- 正常系は3つ程度、異常系は3~5つ程度とする。（目安）
  - 異常系は考え出すとキリが無いので、ほどほどにする。

例:
```markdown
### {logicname}

- {処理その１}
- {処理その２}
- {処理その３}

#### テスト：正常系
- {期待される結果1}
- {期待される結果2}
- {期待される結果3}

#### テスト: 異常系
- {期待される結果1}
- {期待される結果2}
- {期待される結果3}
- {期待される結果4}
- {期待される結果5}
```
