# docs 整理ルール

ドキュメントの置き場とライフサイクルの正本。矛盾がある場合は本ファイルを優先する。

各プロジェクトでは `docs/` 配下に置く。本リポジトリ（charter 正本）では `charter/` が文書の置き場であり、`docs/charter/` 相当である。

---

## 1. ディレクトリの役割

| パス | 役割 | アーカイブするか |
|------|------|------------------|
| `docs/wishlist.md` | PO の個人メモ。未整理・未転記のみ | 完了メモは `_archived` 可 |
| `docs/plans/` | **これからやる**内容。詳細済みでも未実装ならここ。意図スタブもここ。**版ごと**にサブフォルダ（例: `vX.Y.Z/`）。未割当は `unscheduled/`。索引は直下 | 実装後は原則 `specs/` へ移し、空なら削除 |
| `docs/specs/` | **現行バージョンに存在する**機能の仕様正本。ドメイン別に分割（`docs/tests/` と同じ切り方） | 機能が最新から消えたときだけ `_archived` へ |
| `docs/charter/` | プロジェクトの絶対ルール（例: TDD、薄い DDD）。変更はあり得る | **`_archived` へは移さない** |
| `docs/_archived/` | 最新から削除・置き換えられたもの、および歴史資料 | ここが終着 |
| `docs/tests/` | テスト仕様（TDD の入力）。ドメイン別 | 現行のまま（本整理の主対象外） |
| `docs/resources/` | サンプルデータ等の付随ファイル | 同上 |
| `docs/` ルート | ハブのみに限定（後述） | — |
| `docs-agent-note/`（リポジトリ直下） | **Agent の一時メモ**。正本ではない | マージ後に正本へ転記して **消す** |

### ルートに残すもの

- `main.md` … プロダクト目的・スコープ・技術方針の索引／正本ハブ
- `roadmap.md` … SemVer・マイルストーン一覧・進捗のハブ
- `wishlist.md` … PO メモ
- （任意）`er.dbml` … DB を持つプロジェクトの ER 設計用（実装スキーマはマイグレーションが正）

`tdd.md` / `thin-ddd.md` などは `charter/` へ置く。  
ユースケース一覧を置く場合は `specs/` へ置く。

---

## 2. 文書のライフサイクル（順序）

```markdown
1. wishlist に PO がメモを残す
2. LLM 等と相談し、やることを決めたら plans/ に書く
   - 詳細が後日でよい → 意図スタブでよい
   - 詳細まで詰めた → そのまま厚い plans でよい
3. 実装が終わったら plans/ → specs/ へ移動（新規機能）
4. 既存機能の変更なら specs/ を直接更新
   - 大きな未実装差分があるなら、specs 更新と並行して plans/ 新規も可
5. 機能がプロダクトから削除されたら specs/ → _archived/ へ
```

### plans 内の段階

| 段階 | 意味 | plans に書くこと |
|------|------|------------------|
| **意図スタブ** | やりたい。詳細は後日 | 目的・ざっくり範囲・やらぬこと（任意）・版 or 時期未定 |
| **方針確定** | やり方の骨格は決まった | 上記＋方針・制約・版 or 時期未定 |
| **仕様詳細** | 実装に入れる粒度 | 受け入れ条件・データ・UI・テスト方針の参照 など |

「意思決定事項」という言葉は使わない。  
A/B の選択待ちではなく、**詳細仕様を後で詰める枠**を指す場合は「意図スタブ」「後日詳細」と呼ぶ。

---

## 3. wishlist ルール

- **確定した計画・仕様の正本にはしない。** 転記したら wishlist からは消すか、「正本は `plans/xxx`」へのリンクだけ残す。
- 雑多な dogfooding・思いつきはここに置いてよい。
- 実装済みの長いメモを残したいときだけ `_archived/` へ退避する。

---

## 4. plans/ ルール

### ディレクトリの切り方

| パス | 内容 |
|------|------|
| `plans/` 直下 | 索引のみ（`README.md` / `future-intents.md`） |
| `plans/vX.Y.Z/` | そのマイルストーンで実装する計画（roadmap の版名に合わせる） |
| `plans/vX.Y+/` 等 | 仮号数・帯だけのとき（後期まとめなど） |
| `plans/unscheduled/` | マイルストーン未割当 |

版が決まったら `unscheduled/` から対応版フォルダへ移す。

### 置くもの

- 未実装の機能仕様（厚いもの）
- 意図スタブ（薄いもの）
- 実装時期・版の割当に関する **索引**（バックログ相当）— 直下
- 「将来やりたい一覧」の索引（中身は意図スタブへのポインタ）— 直下

### 各ファイル冒頭に推奨するメタ

- **状態**: `意図スタブ` / `方針確定` / `仕様詳細`
- **マイルストーン**: `vX.Y.Z` など、または **`unscheduled`**（フォルダと一致させる）
- （任意）依存・前提、関連 `specs/` / `roadmap` へのリンク

### 置かないもの

- すでに現行に実装済みで、生きている仕様の正本 → `specs/`
- 憲章 → `charter/`
- テスト手順の詳細 → `tests/`（plans からは「実装時に tests を書く」程度）

### 実装後

- 新規機能: ファイルを `specs/` の対応ドメインへ **移動**（コピー放置しない）
- 既存拡張で plans に差分だけ置いていた場合: specs にマージしたら plans 側は削除、または短いものを `_archived` へ
- 版フォルダが空になったらフォルダごと削除してよい

---

## 5. specs/ ルール

### 置くもの

- **いまのアプリに存在する振る舞い**の仕様正本
- 運用手順のうち現行のもの（例: DB migrate）もここに含めてよい

### 更新の仕方

| ケース | 操作 |
|--------|------|
| 既存機能の改善・バグ修正に伴う仕様変更 | **`specs/` を直接更新** |
| 大きな新機能として切り出せる未実装部分がある | specs を直しつつ、未実装塊は `plans/` 新規でも可 |
| 機能そのものを廃止 | 該当 spec を `_archived/` へ移す |

### 置かないもの

- 未実装の案・スタブ → `plans/`
- 「案」「版未割当」だけの長い将来仕様 → `plans/`
- 完了マイルストーンのチェックリスト履歴 → `_archived`（履歴用）

### 一部実装・一部未実装が同じテーマのとき

- **現行部分は `specs/` に残す**
- **未実装節だけ**を `plans/` に切るか、specs 内に「未実装・詳細は plans/xxx」と明示してリンクする
- 無理にファイルを割らなくてよい。迷ったら「現行の正本は specs、未実装の作業単位は plans」

---

## 6. charter/ ルール

- 開発プロセス・アーキの **守るべきルール**（TDD、薄い DDD など）
- 改訂してよいが、**旧版を `_archived` に移して「なかったこと」にはしない**（履歴が必要なら charter 内で版注記、または git 履歴を正とする）
- プロダクト要件の本文（目的・スコープの詳細）は各プロジェクトの `main.md` / `specs/` に残し、charter に詰め込まない

---

## 7. _archived/ ルール

### 入れるもの

1. **最新プロダクトから削除・置換された仕様**（旧 `specs` の残骸）
2. **歴史資料**（完了マイルストーンの詳細チェックリスト、旧ワイヤー、実装済み dogfooding の退避など）

### ディレクトリの切り方

- **削除された仕様**は、可能なら docs と同じ相対パスを維持する（オーバーライド的）
  - 例: 現行が消えた `specs/{domain}/foo.md` → `_archived/specs/{domain}/foo.md`
- **完了履歴・dogfooding**はミラー対象外でもよい。例: `_archived/history/` やフラット配置 + README で区別

### 入れないもの

- 現行仕様の正本
- charter
- 「まだやるつもり」の plans（未実装は archived ではない）

### README

- `_archived/README.md` で「現行の正本ではない」こと、および **削除仕様** vs **歴史資料** の一覧を保つ

---

## 8. roadmap / 索引との関係

- `roadmap.md` … 版一覧・状態・短い受け入れのハブ。詳細仕様の正本にはしない
- `plans/README.md` … 版フォルダ索引・実装順・依存・後期仮順序
- 個別の厚い内容は必ず **個別の plans または specs ファイル**が正本。索引だけに詳細を書かない
- wishlist の「正本」列は、転記後は `plans/` または `specs/` を指す

---

## 9. tests/ との関係

- 版を切って実装に入るとき、TDD に従い `docs/tests/` にテスト仕様を書く
- plans / specs は「何を作るか」、tests は「何を検証するか」
- 実装完了後も tests は残す（仕様の回帰の正本の一部）
- `specs/` と `tests/` は同じドメイン分割にする。ドメイン名は各プロジェクトに依る

---

## 10. 実装と設計の並行（Agent / worktree）

実装を worktree 上の Agent に任せつつ、main 側で docs を気軽に編集するためのルール。  
コンフリクトの本丸は worktree 自体ではなく、**同じ Markdown を両側で書き換えていること**。

### 触ってよいもの / 触らせないもの

| 側 | 触ってよい | 触らない |
|----|------------|----------|
| **実装 worktree / Agent** | コード + 当該機能の `docs/tests/` + 必要なら `docs-agent-note/` | `docs/plans` / `roadmap` / `wishlist` / `specs`（plans→specs 昇格も含む） |
| **main（PO・設計）** | wishlist / plans / roadmap など自由。できれば「今実装中の版」以外（次版・`unscheduled`・wishlist）に寄せる | 実装ブランチが所有する当該 `docs/tests` はなるべく触らない |

### `docs-agent-note/`

- Agent がファイルとして残したいメモ（未決・後で正本へ書きたい差分など）はここに短く置く
- **正本ではない。** マージ後に `plans` / `specs` / `tests` などへ転記し、ノートは削除する
- 日常の「なぜこう実装したか」は PR / コミットメッセージで足りることが多い。ノートは必要なときだけ

### マージ後

- `docs-agent-note/` の内容を正本へ反映してから消す
- plans→specs など正式 docs の更新は **main 側**で行う（実装ブランチではやらない）

---

## 11. 命名・リンク運用

- ファイル移動したら、`main` / `roadmap` / `wishlist` / 他 docs からの相対リンクを更新する
- 移転スタブ（リダイレクトのみのファイル）は、移行完了後に残さない（または一行リダイレクトだけにして早めに消す）
- plans → specs 移動時は **同じベース名**を維持し、`specs/` 側は tests と同じドメインサブフォルダへ置く

---

## 12. 文末

ファイルの最後は、最後であることを明示するため

```markdown

----

以上
```

と書く。

## 13. やってはいけないこと

- 未実装案を `specs/` に置きっぱなしにする
- 実装済み正本を `plans/` に残したままにする（移動忘れ）
- wishlist に決定済みの長い仕様を溜め込む
- 削除でもない完了チェックリストを「現行 specs の代わり」として読む
- charter を archived してルールの所在を不明にする
- 「意思決定」と「意図スタブ（後日詳細）」を同じ言葉で混ぜる
- 実装 worktree の Agent に `plans` / `roadmap` / `wishlist` / `specs` を編集させる
- `docs-agent-note/` を正本扱いのまま残す（転記忘れ）

---

## 14. ワンライナー

**思いつきは wishlist、やることは plans（薄くて可）、動いていることは specs、消えたことは archived、守ることは charter。Agent の一時メモは docs-agent-note（転記して消す）。**
