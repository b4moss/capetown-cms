# Git運用のルール

## リモート

以下の2つのうち、いずれか、または両方を採用する。

- GitHub
- セルフホストGitea（合同会社 知的・自転車内部インナー利用）

補足:
- メインとなる remote の名称は `origin`
- 2つ目以降の remote 名称は、その目的や由来に応じて適切な名称を設定する

## ブランチ

- ブランチは、開発初期においては`develop`をメインブランチとする。
- 開発が進むと、`main`を作成する。
- 必要に応じて、以下のブランチを用意する。
  - `staging`: ステージング環境用のブランチ。必ずmainからPRし、マージする。
  - `production`: 本番環境として運用されるもののブランチ。必ずmainからPRし、マージする。
  - `release`: SaaSやWebサイトでなくパッケージマネージャから配信されるものはこのブランチをプロダクション相当とする。
- ロードマップに従った開発を行うブランチ: `dev-vX.Y.Z` - 必ず、最新のdevelopから新規ブランチを生やす。
- フィーチャーブランチ: `feat-*` - 新規追加機能の場合に作成するブランチ。
  - 機能ごとに適切なブランチの適切なコミットから生やす。
  - 何が適切かはその時の文脈次第なので、適切なブランチ・コミットの判断がつかない場合は、POに事前相談する。 
- Hotfix: 緊急に修正し対応する場合は `hotfix-{slug}` を作成し、必要なブランチへPRする。
  - マージ後、他のブランチへは適切にマージする（実装者が各自に手作業で行う。マージが作業に悪影響を及ぼすなら、無理に行わなくて良い）

## PR&マージルール

### ロードマップ上のバージョンを満たす実装が終わった時

- `dev-v0.n.0` - PR -> `develop`: CIを必ず通すこと。

### ステージングで確認したい場合

- (新機能を統合した)`develop` -> `main` - PR(PR時にCI。念のため) -> `staging`(マージ時にCD)

### プロダクションへのリリース

- (新機能を統合した)`develop` -> `main` - PR -> `production`(マージ時にCD): stagingマージ時にCIが通ったものとみなす

### 直接push禁止ブランチ

- main
- develop
- staging
- production

ただし、上記4つのブランチは、POがforce pushした場合は、受け付けること。（緊急時の対応）

### ブランチの生やし順

1. develop
2. main
3. staging
4. production

最初から全てのブランチが必要ではない。開発の成長に応じて増やしていく。
但し、最初はdevelopが正。

## コミットの切り方

### ソースコードの場合

- 1ファイル1コミットを原則とする
- 1ファイルにおける変更が大量に渡る場合は、コンテキストに応じてハンクコミットして良い
- コンテキストに応じて、複数のファイルやハンクを1つのコミットにまとめない
- コミットメッセージは、英語。「何をどうしたか」を簡潔に明記。詳細に書きすぎない
  - コミットメッセージは、あくまで人間が読むための「目安・インデックス」にすぎない
  - 変更の意図をコミットで深く伝えようとしない。意図は、diffから汲み取る

### ドキュメントの場合

- コンテキストやテーマごとに応じて、複数ファイル・複数ハンクのコミットを許容する
